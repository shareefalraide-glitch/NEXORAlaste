# 📘 توزيع العمل على فريق من خمسة أشخاص

هذه مسؤوليات مقترحة **وليست أسماء أو صلاحيات GitHub فعلية**. يختار الفريق أسماء الأعضاء ويعدّل الأحمال. لا تقدير زمني مُلزِم هنا؛ الانتقال بين المراحل مرتبط ببوابات تحقق لا بعدد الأسابيع.

| الرمز | الدور والمسؤولية | نطاق البداية |
|---|---|---|
| **P1** | قائد المنصة والأمن والتشغيل | الهوية، التفويض والعزل، TLS والأسرار، التدقيق، النسخ والمراقبة. |
| **P2** | مهندس الاستشعار والبيانات | Zeek أو Suricata، Vector، مخطط الحدث، الأصول والإثراء، PostgreSQL/Timescale وسياسات البيانات. |
| **P3** | مهندس الكشف وML | Sigma وSuricata، السمات، Isolation Forest، المعايرة والحوكمة والشرح وIoC/MITRE. Python لخدمات الكشف فقط. |
| **P4** | مهندس أعمال الحوادث والاستجابة | Go/Fiber، الربط ودورة الحوادث، الموافقات والأدلة والموصل والإشعارات. |
| **P5** | مهندس React وتجربة المحلل والجودة | عميل API، الواجهات والرسوم، التقارير والتصدير، اختبارات المتصفحات والقبول والوصول. |

كل تغيير يُراجع من عضو آخر: يراجع P1 تغييرات الأمن والتفويض، وP2/P3 عقد الحدث والكشف، وP4/P5 تجربة الحادثة والتصدير. مراجعة الأمن ليست بديلًا عن متخصص خارجي عند الحاجة.

## 📖 بوابات التنفيذ

1. **تثبيت الأساس:** تأكيد العقد والحدود، مستودع خاص وCI، بيئة معزولة، جرد الأسرار ومصفوفة الأدوار. يعتمد هذا على `P1-01` إلى `P1-03` و`P5-01`.
2. **شريحة الحدث:** P2 يبني مستشعرًا واحدًا وخط Vector وتطبيعًا وتخزينًا؛ لا يُطلق عليه كشفًا. تُختبر السجلات، الزمن، التكرار، الصلاحيات وقياس الحمولة (`P2-01`–`P2-05`).
3. **شريحة الكشف:** P3 يسلّم القواعد ثم السمات وخط الأساس والتدريب والمعايرة والتقييم؛ لا تعتمد أرقام المعاينة نموذجًا فعليًا (`P3-01`–`P3-05`).
4. **الحادثة والاستجابة:** P4 يربط تنبيهًا موثقًا بحادثة ويكمل دورة الحياة والتدقيق، ثم يُنفذ موصل واحد بعد موافقة بشرية ونتيجة متحقق منها (`P4-01`–`P4-04`).
5. **الواجهة والقبول:** P5 يربط العرض بالبيانات الحقيقية، ويختبر الفراغ والصلاحية والخصوصية والتصدير مع محللين وبالمتصفحات؛ يثبت الفريق تفاصيل 1.7 قبل اعتمادها (`P5-01`–`P5-07`).
6. **جاهزية التشغيل:** فحوص الحِمل والسعة والنسخ والاستعادة والاختبار الأمني ومراجعة الوصول، وتوثيق النتائج والقيود. أهداف التقرير مثل 2000 حدث/ثانية وRPO/RTO أهداف غير محققة حتى تُقاس.

تجري المهام التي لا تتعارض بالتوازي، لكن لا يُربط الخادم بخدمة تدعي نتائج غير موجودة. تمثل حالات `null / unavailable / unknown` نقص المعلومات لا صفرًا أو سلامة.

## 📖 البطاقات الجاهزة

يوجد **31 ملف Issue** تحت [`issues/`](issues/)، لكل منها هدف واعتماديات ومتطلبات ومعايير قبول ومالك مسار مقترح. راجعوها وعدّلوا الأولوية قبل الإنشاء. استخدم:

<div dir="ltr">

```bash
sh scripts/prepare-github-issues.sh                    # عرض محلي فقط؛ لا يتصل بـGitHub
sh scripts/prepare-github-issues.sh --apply OWNER/REPO  # ينشئ Issues حقيقية بعد gh auth
```

</div>

الطريقة الثانية تتطلب GitHub CLI وصلاحية إنشاء Issues. لا تُسند أعضاء أو ملصقات تلقائيًا، وإعادة تشغيلها قد تنشئ تكرارات؛ راجع نتيجة التشغيل الأول قبل أي إعادة. لم يُنفذ الأمر المنشئ هنا.

## 📖 تعريف الإنجاز لكل مهمة

- عقد API أو قرار موثق، مع توافق الإصدارات ونموذج بيانات وهجرة عند الحاجة.
- مراجعة صلاحية المورد وعزل المؤسسة والخصوصية والأسرار والتدقيق؛ لا سر أو سجل حقيقي في الاختبارات العامة.
- اختبارات نجاح ورفض وتزامن/حالات حدّية مناسبة، وإرفاق نتائجها بوضوح، مع توثيق ما تعذر اختباره.
- لا احتواء دون موافقة بشرية على الإجراء المحدد وموصل موثوق ونتيجة متحقق منها.
- مراجعة PR مستقلة وتحديث حالة العملية من `planned` إلى `implemented` فقط عند وجود كود واختبارات مطابقة، وإزالة العملية من ملف المسودة.
- لا توصف المعاينات أو fixtures أو حسابات غير معايرة بأنها كشف حقيقي، ولا تُقدَّم نتائج أدوات الفحص كقبول بشري.
