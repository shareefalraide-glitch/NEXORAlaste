# وضع API الفعلي في واجهة NEXORA

أُضيف وضع تشغيل اختياري للواجهة يتصل بشريحة Go/Fiber الموجودة. الوضع الافتراضي يبقى نموذج Demo الحالي؛ لا يغيّر وضع API بيانات النموذج أو يدّعي أن خصائصه العديدة متصلة. عند تفعيل API، يعرض التطبيق مساحة API منفصلة مصدرها طلبات الخادم فقط.

## الإعداد والتشغيل المحلي

1. جهّز PostgreSQL والخادم حسب `README.md` و`docs/DEVELOPMENT.md`، وشغّل migrations وتهيئة أول مدير مؤسسة. تحتاج المؤسسة مستخدمًا حقيقيًا وكلمة المرور التي أدخلتها عند bootstrap.
2. من مجلد `frontend/` انسخ ملف الإعداد المثال إلى إعداد تطوير محلي:

<div dir="ltr">

```bash
cp .env.example .env.local
```

</div>

3. غيّر `VITE_NEXORA_AUTH_MODE=api`. عدّل `NEXORA_API_PROXY_TARGET` فقط إذا كان عنوان خدمة Go مختلفًا؛ يقرأ Vite هذا المتغير في الخادم ولا يكشفه لمتصفح المستخدم. لا تضف `/api/v1` إلى هدف الوكيل.
4. شغّل `npm ci && npm run dev`. يرسل المتصفح طلبات نسبية إلى `/api/v1`، ويعيد Vite توجيهها من جهة الخادم. لا يطلب كود المتصفح `localhost` لخدمة API.
5. استخدم معرف المؤسسة، البريد وكلمة مرور عضوها. لا توجد كلمة مرور افتراضية أو رمز تحقق تجريبي في وضع API.

لا تُضمّن `.env.local` في التسليم. إعداد Vite يتضمن proxy في dev وpreview؛ أما استضافة `dist` كملفات ثابتة وحدها فلا تنشئ proxy إنتاجيًا، لذلك وفّر reverse proxy server-side متوافقًا. لا يضيف هذا الإعداد CORS أو HTTPS للإنتاج.

## المصادقة والجلسة

- يرسل النموذج `organization`, `email`, `password` إلى `POST /api/v1/auth/login` ثم يتحقق من الجلسة عبر `/auth/me`.
- تبقى رموز الوصول والتجديد في ذاكرة JavaScript فقط، ولا تحفظ في localStorage أو sessionStorage؛ إعادة تحميل الصفحة تتطلب تسجيل الدخول مجددًا.
- تُجدّد الجلسة مرة واحدة عند 401 باستخدام refresh token دوّار، وتتشارك الطلبات المتزامنة عملية التجديد الواحدة. رفض التجديد يمسح الرموز.
- الخروج يطلب إبطال الجلسة عبر `/auth/logout` ثم يمسح الرموز محليًا. إذا تعذر الوصول إلى الخادم عند الخروج فلا يمكن ضمان إبطال الخادم؛ انتهاء صلاحية الجلسة يظل حدًا إضافيًا.
- التفويض الفعلي على الخادم هو المرجع. تخفي الواجهة بعض عناصر الوصول فقط لتحسين الاستخدام، ولا تعتبر ذلك بديلًا عن صلاحية API.

## العمليات المتصلة

| مساحة الواجهة | العمليات الفعلية |
|---|---|
| الملخص | `GET /dashboard/summary`؛ تعرض الأحداث والحوادث المفتوحة وعدد الأصول والمصادر، وتعرض التنبيه والكشف بوضوح «غير متاح/غير منفذ». |
| الأصول | `GET /assets`; للمسؤول فقط نموذج `POST /assets`. |
| المصادر | `GET /sources`; لا تدّعي الشاشة اتصال مصدر حيًا ولا تعرض رمز إنشاء جديد. |
| الأحداث | `GET /events` للجزء المخزّن الحالي. لا توجد قواعد كشف أو إثراء في الواجهة. |
| الحوادث | `GET /incidents`; للمسؤول/المحلل/المستجيب إنشاء حادثة بـ`POST /incidents`؛ عرض التفاصيل والملاحظات والمهام؛ الملاحظات بـ`POST /incidents/{id}/notes`، والمهام بـ`GET/POST/PATCH /incidents/{id}/tasks`. |
| التدقيق | للمسؤول أو المدقق `GET /audit` والتحقق بـ`GET /audit/verify`. تعرض الواجهة تحذير أن الفحص لا يتحقق من مرساة خارجية. |
| المستخدمون | للمسؤول `GET /users` للقراءة؛ لا توفر الواجهة الحالية إنشاء مستخدمين. |

تُجلب 50 نتيجة لكل صفحة من هذه المساحات ويتيح شريط التنقل جلب إزاحات لاحقة. البحث والتصدير في الواجهة يخصان النتائج المحمّلة حاليًا فقط. الأخطاء أو الاستجابات الفارغة لا تستبدل بيانات Demo.

## ما لا يتصل بعد

الوضع لا يربط بقية شاشات React الأصلية (التنبيهات، قواعد الكشف، الرسم الشبكي، المحاكاة، التقارير الموسعة، وميزات التحقيق الأخرى). لا يعرضها كأنها بيانات API؛ يستخدم مساحة منفصلة محدودة. لا يوجد كشف آلي أو تدفق أحداث مستمر أو WebSocket. لا يمكن إتمام سيناريو كشف تنبيه وحادثة لأن القواعد والتنبيهات الآلية غير موجودة في Backend.

## اختبارات الوضع

- `tests/unit/api-client.mjs` يختبر سلوك عميل HTTP باستجابات mock: تسجيل الدخول، ترويسة Bearer، تجديد رمز single-use، تسجيل الخروج ورفض جلسة منتهية.
- `tests/unit/api-proxy.mjs` يشغّل Vite وupstream mock محليًا على منفذ مؤقت ويتحقق من تمرير `/api/v1` إلى target المُعد. هذا يثبت إعداد proxy فقط، لا يثبت Go أو قاعدة بيانات.
- اختبارات React/browser لازمة لفحص العرض والتفاعل كاملًا. لاختبار API الحقيقي يلزم تشغيل Go/PostgreSQL وإعداد حساب مؤسسة؛ لا تستخدم قاعدة بيانات حقيقية أو بيانات حساسة في الاختبارات.
